# What for lunch？

手机优先的午饭餐厅选择网页，按 375×812 原型实现。顶部最多八张推荐卡片可左右滑动；剩余餐厅保留在底部的 1/3 大小卡片堆。网页现在从项目中的 beichen_restaurants_2km_full.json 加载 380 家北辰餐厅；以前浏览器里的示例清单不会再用于推荐，也不会被删除。底部最多展示 50 张未进入当前推荐的卡片。

## 启动

双击 `Start.command`，保持终端运行，然后打开 http://127.0.0.1:4173/。

也可以在项目目录运行：

```sh
LUNCH_DECIDER_HOST=0.0.0.0 python3 server.py
```

同 Wi-Fi 的手机通过 `http://电脑局域网IP:4173/` 访问。若已有旧服务占用 4173 端口，先关闭旧服务。

需要 Python 3.9 或更新版本，无第三方 Python 依赖。模型通过网络调用。修改代码后请重启本地 Python 服务。

## 午饭标签与推荐规则

页面提供“随机”及以下九个标签，单选，不增加菜系选择器。标签固定为两行、每行五个，按文字长度呈现宽度差异：两字窄、三字较宽、四字更宽，高度与行内位置对齐，顺序固定；选中态仍使用黄色。窄屏同步缩放宽度与间距，保留两行布局。同一家餐厅可以符合多个标签，定义不互斥；仅所选标签参与当前推荐。

| 标签 | 字段 | 定义与典型餐食 | 边界 |
|---|---|---|---|
| 米饭 | `rice` | 米饭为主要主食，如盖饭、炒饭、煲仔饭、咖喱饭、小炒配饭。 | 以主营或招牌米饭午餐为准；面馆、米线米粉店不能靠一道附带盖饭或可加米饭进入。米线、米粉、年糕不是米饭。明确以饭面双主营的店可交由模型判断。 |
| 面食 | `noodles` | 面粉制品为主要主食，如面条、饺子、馄饨、包子、饼。 | 以主营或招牌面粉主餐为准；火锅加面、烤肉配饼、米饭店附带面条不算。米线、米粉、年糕、土豆粉和粉丝不归入此标签。 |
| 带汤的 | `soup` | 可喝的汤是餐食重要部分，或有明确、足量的汤品搭配，如汤面、米线、馄饨、汤饭、炖汤套餐、汤锅。 | 必须明确有足量、可喝的汤；干拌面、浓酱、勾芡、干锅、少量赠汤不算；仅用于涮煮的火锅底汤不算，面馆名称本身也不能证明有汤。 |
| 健康的 | `healthy` | 少油少盐、减脂或搭配均衡的健康风格餐食，如轻食、清蒸鱼套餐、白灼菜、少油荤素套餐。 | 不要求素食或沙拉；依据主要、常规午餐判断；少量沙拉、汉堡中的蔬菜、假设去酱或特殊点单不构成符合。主要餐食为炸鸡、汉堡、薯条且无明确健康主餐证据时，应低于匹配门槛；资料不足也不能达到门槛。有蔬菜、普通荤素搭配、瘦肉、鱼、寿司、汤或名称带“轻食”不足以高度符合；需要少油少盐、清淡制作或健康完整主餐的明确证据。不代表已验证的营养、卫生或医疗效果，不编造热量、营养数值。 |
| 放纵的 | `indulgent` | 高热量、油脂丰富或浓厚丰盛，满足“今天吃得爽”的需求，如炸鸡、肥肉烤肉、芝士披萨、浓奶油意面、油脂丰富的火锅。 | 以主营或招牌的油脂丰富、油炸、芝士奶油等浓厚餐食为准；小份炸物配菜、普通份量、仅很辣很咸很酸、仅有肉不算。清淡瘦肉不自动算放纵。不编造实际热量。 |
| 重口的 | `heavy_flavor` | 中餐语境下，重油、重盐、重辣、重麻或浓酱带来明显味觉刺激，如麻辣香锅、重辣川湘菜、浓味干锅、重油重酱小炒。 | 必须有重油重盐重辣重麻浓酱的明确主餐证据；川湘菜品类、店名、普通调味、蘸料、可加辣或辣味配菜不能单独证明。汉堡、炸鸡、烤肉不自动属于中餐重口。可以不辣；没有独立辣度评价。 |
| 吃肉 | `meat` | 畜禽肉是餐食主角，满足大口吃肉的需求，如地锅鸡、烤肉、牛排、排骨锅、炖牛肉、烤鸭。 | 不包含鱼虾及其他海鲜；少量肉丝、肉末、肉汤、普通汉堡肉饼、普通牛肉面或饺子肉馅不能单独证明肉是主角。肉量足且肉是主角的饭面可以符合；不要求油腻或重口。 |
| 换个口味 | `variety` | 尝试日常中式饭菜之外的餐食风格，如寿司、日式定食、韩料、泰餐、越南餐、非快餐式西餐。 | 排除汉堡王、麦当劳、肯德基、赛百味等西式汉堡、炸鸡、三明治快餐连锁；这些店仍可在其他标签下推荐。广泛探索，不保证指定菜系；常见中式地方菜不因味道重或菜名特别就高度符合，不推断用户个人饮食历史；需要明确的非中式主营餐食，洋气店名或一道异国配菜不算。 |
| 快餐 | `quick_meal` | 适合午休时间有限、快速解决一顿饭的单人份、套餐或简餐形式，如中式快餐、盒饭、自选菜套餐、汉堡套餐、饭团套餐、简餐盖饭。 | 不等于油炸或不健康；长时间制作、多人共享或完整长流程用餐只能弱匹配。必须有完整单人餐或快餐服务形式的明确证据；人均价格低、适合少人数、能单人吃或偶有套餐不等于快餐。小炒点菜、烤肉、火锅、多人共享和长流程用餐不靠猜测小份餐进入。不保证出餐分钟数，不把距离重复计入。 |

“带汤的”替代“热乎的”，“健康的”替代“干净的”，“换个口味”替代“地方菜”，新增“快餐”。页面和服务端同步使用新标签及字段。选择“换个口味”时，已识别的洋快餐品牌或明确标注为西式快餐的候选先排除，再调用 Jev；模型也会将同类洋快餐判为该标签不匹配。仅“快餐厅”等笼统品类不据此排除，日式、韩式套餐也不因出餐快而排除。

例子：炸鸡汉堡套餐可符合快餐、放纵的，但普通肉饼不能直接证明符合吃肉；大份炸鸡明确以肉为主时可符合吃肉；少油鸡胸肉饭可符合米饭、健康的、快餐，肉是主角时也符合吃肉；麻辣素香锅可符合重口的，油脂丰富时也符合放纵的；日式拉面可符合面食、带汤的、换个口味。

### 主营证据与明确排除

九个标签统一依据主营、招牌和常规完整午餐判断，不能靠“菜单可能有”、零星配菜、可加料、假设定制或笼统菜系印象匹配。标签可以重叠，但每个都要独立有证据。资料不足、主餐相反或仅有边缘菜品时，匹配必须低于 0.6；缺少符合者时不降低要求补位。

米饭增加确定性候选排除：店名或明确品类表示面馆、拉面、牛肉面、米线米粉等专门店，且店名或品类没有明确盖饭、炒饭、饭面等米饭主营标识时，调用模型前排除；菜单中的附带盖饭不解除排除。饭面双主营标识只保留候选，仍需模型过门槛。洋快餐在换个口味中的既有排除继续保留，其他标签不受这两项排除影响。

### 标签匹配门槛

`MIN_TAG_MATCH = 0.6`：选择明确标签时，先要求该标签的 Jev 匹配分 ≥0.6，低于门槛不进入推荐列表，再对符合者按综合推荐值排序。评分高、距离近或人数适配好不能抵消标签不匹配。API 主动启用多个标签时，所有启用标签都需过门槛。

“随机”没有标签门槛，仍按人数适配、评分和距离排序。门槛针对标签匹配分，不是综合推荐值，也不是满意概率。最多展示 8 家，不足时只展示实际符合者；没有符合者时返回空列表并提示调整条件。前端严格使用服务端推荐列表，不从未过门槛的候选中补位。

### 推荐值权重

`scoring.py` 保存基础权重、标签模型判断规则及确定性评分公式。基础权重是相对值，不是固定百分比。

| 维度 | 基础权重 | 启用条件 |
|---|---:|---|
| 标签匹配 | 40 | 选择九个标签之一；“随机”不启用。九个标签使用相同权重。 |
| 餐厅评分 | 25 | 始终启用。 |
| 距离 | 15 | 始终启用；已从 10 提升至 15。 |
| 人数适配 | 10 | 所有人数始终启用 `party_size_fit`；Jev 根据实际用餐人数判断餐食、份量和点单形式是否合适。 |

仅启用的维度参与归一化：`归一化权重 = 基础权重 / 所有启用维度的基础权重之和`。

- 选择标签、任意人数：合计 90；标签 44.44%、评分 27.78%、距离 16.67%、人数适配 11.11%。
- 随机标签、任意人数：合计 50；评分 50%、距离 30%、人数适配 20%。仍调用 Jev 判断人数适配。

辣度选择控件、独立辣度模型问题、辣度匹配公式和权重已移除。“重口的”继续按重油、重盐、重辣、重麻等综合口味定义，不自动改成“香辣的”；“放纵的”仍不保证辣味。旧客户端传入的 `spice` / `spiciness` 会被忽略，不参与推荐。

`综合匹配分 = Σ(维度匹配分 × 归一化权重)`；页面显示 `推荐值 = round(综合匹配分 × 100)`。推荐值是综合匹配程度，不是满意概率，也不是模型置信度。

### 人数适配规则

原来的仅 1 人启用的 `solo_friendly` 已替换为所有用餐人数都启用的 `party_size_fit`，不叠加两个维度。前端继续传 `people`，服务端将验证后的实际人数传入 Jev 的每道人数适配问题。

- 1 人：明显偏向单人份、快餐、完整的个人套餐，避免需要独自点多道共享菜的形式。
- 2 人：个人套餐仍很合适，也接受适合两人分享的小份菜、双人餐。
- 3–4 人：个人套餐与共享点菜均可，结合份量、搭配和点单灵活度判断。
- 5 人及以上：人数越多，越偏向可点多道菜、共享餐食、大份菜、拼盘或锅类。

上述人数段只用于表达逐渐变化的软偏好，不作为新的硬排除条件。快餐并非不能接待多人，大份菜也不自动代表宴席；少人数也可选择份量合适的共享餐食。标签仍表达食物偏好，人数适配独立评价具体人数下的用餐形式，不重复计入口味、热量或距离。

未知桌位、容量、最低消费、份量或服务形式时保持不确定，不编造事实；“大份”不等于已确认座位足够。数据中明确的人数容量限制仍在调用 Jev 前筛选。

### 各维度评分与筛选

- 标签和人数适配：Jev 的 Noul 判断为 0–1，允许重叠；资料不足时保持不确定，不编造餐厅事实。
- 评分：`max(0, min(1, (rating - 3.5) / 1.2))`，缺失或无效时为 0.5。
- 距离：使用数据集中的 `distance_m`，不是用户实时位置。≤300 米为 1，≤600 米为 0.85，≤1000 米为 0.65，≤1500 米为 0.35，≤2000 米为 0.15，超过 2000 米为 0；缺失时为 0.5。
- 预算与明确的人数容量限制先筛选，不参与加权，不能用高评分抵消不合适的价格或容量。缺少价格的餐厅显示“暂无价格”，暂不进入预算筛选；未知容量保留为空，不据此硬排除，也不保证可接待人数。

服务器返回最高的 15 个餐厅 ID，页面每批展示最多 8 张推荐卡片。餐厅照片加载失败或缺失时回退到午餐示意图。服务端也支持新标签字段的布尔输入，页面只发送单选的 `preferredTag`；若 API 客户端主动启用多个标签，每个激活标签分别使用基础权重 40 后一起归一化。

## 配置

桌面版本在项目的 `.env` 保存 `TYPESAFE_API_KEY`，仅服务端读取。也可设置环境变量 `TYPESAFE_API_KEY` 或 `LUNCH_DECIDER_KEY_FILE`。服务只提供明确列出的网页资源，不会提供 `.env`。

## 卡片物理交互

进入页面时，50 张小卡片分批从顶部落下，落地后通过 Matter.js 0.20.0 碰撞与堆积。支持鼠标和手机触摸拖拽，释放时保留甩动速度，可撞开其他卡片。物理层位于筛选块后面，因此经过筛选块时会被遮挡。切换推荐结果保留其余卡片的物理状态，补充新卡片到 50 张；刷新页面或从浏览器缓存重新进入会重新掉落。引擎文件随项目保存，无需另行安装。
