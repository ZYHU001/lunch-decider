# What for lunch？ · Lunch Decider

帮你决定今天午饭吃什么的餐厅推荐网站。选择想吃的类型、用餐人数和人均预算，网站会从北辰周边的餐厅中筛选并排序，让“中午吃哪家”变成几个简单选择。

**在线使用：[lunch-decider-lovat.vercel.app](https://lunch-decider-lovat.vercel.app)**

## 产品做了什么

- **按当下需求找午饭**：提供九个食物偏好标签和“随机”，结合人数与预算推荐餐厅。
- **兼顾一个人和多人吃饭**：少人数更偏向单人餐、套餐；人数越多，越偏向共享点菜、大份菜和锅类。
- **给出可比较的结果**：最多展示 8 家推荐餐厅，卡片显示图片、评分、人均价格和综合推荐值。
- **从推荐走到出发**：点击推荐卡片查看详情、具体地址和距离，有位置资料时可通过“导航”打开苹果地图。
- **让选择过程有点趣味**：底部餐厅小卡片可以拖拽、碰撞和堆积，推荐卡片带有飞入动效。

网站采用手机优先的布局，也可在电脑浏览器使用。当前使用项目内的 **380 家北辰周边餐厅资料**，以北辰新纪元 2 号楼为距离参考点；它不是基于用户实时定位的全国餐厅搜索服务。

## 如何使用

1. 打开网站，选择一个午饭偏好。不确定想吃什么时保留“随机”。
2. 调整人数，范围为 **1–20 人**。
3. 拖动人均价格滑块两端，设定预算范围，支持 **¥5–¥100**，默认 **¥15–¥35**。
4. 点击 **Let's go!!**，等待推荐结果。
5. 左右滑动查看餐厅，点击感兴趣的卡片打开详情，再按需要导航。

想换一组条件时，调整标签、人数或预算后再次点击按钮。如果没有符合条件的餐厅，可以换标签或扩大预算；网站不会用不符合标签的结果补满列表。

## 可以选择哪些偏好

每次选择一个标签，同一家店可以符合多个标签。

| 偏好 | 适合什么时候选 | 主要边界 |
|---|---|---|
| 随机 | 还没想好吃什么 | 不限制食物标签，仍综合人数、评分和距离排序，并非纯随机抽签。 |
| 米饭 | 想吃盖饭、炒饭、煲仔饭、小炒配饭 | 以米饭主营或招牌午餐为准，面馆不靠附带盖饭进入。 |
| 面食 | 想吃面条、饺子、馄饨、包子或饼 | 指面粉主餐，不包含米线、米粉和粉丝。 |
| 带汤的 | 想吃汤面、汤饭、炖汤套餐等 | 汤要足量、可喝且是餐食的重要部分，赠汤不算。 |
| 健康的 | 想吃清淡、相对少油或减脂餐 | 清汤米线、清汤牛肉锅可较低分进入；明确健康制作的主餐得分更高。 |
| 放纵的 | 今天想吃油炸、烤肉、芝士奶油等浓厚餐食 | 仅辣、咸或有肉不自动符合。 |
| 重口的 | 想吃中餐中的重油、重盐、重辣、重麻或浓酱 | 需要明确主餐证据，可以不辣。 |
| 吃肉 | 想让肉成为这一顿的主角 | 畜禽肉要足量；不含海鲜，少量肉末或浇头不算。 |
| 换个口味 | 想吃日料、韩料、泰餐等日常中式午餐之外的餐食 | 排除汉堡王、麦当劳、肯德基、赛百味等洋快餐。 |
| 快餐 | 想用单人套餐、盒饭或简餐解决午饭 | 依据餐食和服务形式判断，不保证具体出餐时间。 |

## 推荐是如何产生的

网站先按预算和已知人数容量筛选，再排除与标签明确冲突的候选。随后由 **TypeSafe Jev** 判断餐厅主营餐食与所选标签的匹配程度，以及点单、份量形式是否适合当前人数。

选择明确标签时，标签匹配分必须达到 **0.60** 才进入排序。模型依据现有餐厅资料判断，不能靠想象中的菜单、配菜或特殊点单满足偏好。

| 排序维度 | 基础权重 | 判断方式 |
|---|---:|---|
| 标签匹配 | 40 | Jev 语义判断；选择“随机”时不启用。 |
| 餐厅评分 | 25 | 根据数据集评分换算。 |
| 距离 | 15 | 根据距固定参考点的距离分档。 |
| 人数适配 | 10 | Jev 判断单人餐、共享点菜和份量形式的适配度。 |

启用的权重会归一化，再加权计算为 0–100 的**推荐值**。推荐值表示综合匹配程度，不是用户满意概率或营养评价；“健康的”只是餐食风格偏好。清汤、水煮等相对清淡餐的健康匹配分为 0.60–0.70，不能仅凭清淡得到高分。

完整标签边界、健康分档、人数规则和计算公式见 [推荐规则文档](docs/recommendation-rules.md)，实际判断指令与筛选实现位于 [scoring.py](scoring.py)。

## 核心技术

| 技术 | 用途 |
|---|---|
| HTML、CSS、原生 JavaScript | 响应式页面、偏好选择、滑块、推荐卡片和详情交互。 |
| Matter.js 0.20.0 | 小卡片的重力、碰撞、堆积与拖拽；引擎随项目提供。 |
| Python 标准库 | 餐厅数据读取、请求校验、模型调用和确定性加权排序，无第三方 Python 依赖。 |
| TypeSafe Jev（`jev-latest`） | 通过 Noul 0–1 判断标签匹配和人数适配，评分与距离由本地公式计算。 |
| JSON 餐厅数据集 | 保存当前餐厅名称、菜品标签、人均价格、评分、位置和图片等资料。 |
| Vercel + GitHub | 托管前端静态资源和 Python API，通过 GitHub 更新触发部署。 |

浏览器通过 `/api/restaurants` 读取餐厅资料，通过 `/api/choose` 请求推荐。模型请求在服务端分批、并发处理，并对部分暂时性错误重试。当前每次推荐都会调用模型，因此候选较多或外部服务响应较慢时，需要更长等待。

## 本地开发

需要 **Python 3.9 或更新版本**，模型调用需要网络和 TypeSafe API Key。

在项目根目录创建 `.env`：

```dotenv
TYPESAFE_API_KEY=your_typesafe_api_key
```

密钥只由服务端读取，`.env` 已加入 Git 忽略列表。也可通过服务端环境变量 `TYPESAFE_API_KEY` 配置。

运行：

```sh
python3 server.py
```

打开 `http://127.0.0.1:4173/`。macOS 也可双击 `Start.command` 启动并打开页面。修改 Python 代码后重启本地服务。

验证推荐逻辑：

```sh
python3 -m unittest discover -s tests -v
```

## 部署与维护

项目通过 GitHub 连接 Vercel。将修改推送到已连接的 `main` 分支后，Vercel 自动构建部署；最新生产部署显示 **Ready** 后生效。

- 在 Vercel 项目的环境变量中配置 `TYPESAFE_API_KEY`，生产环境需要该变量；新增或修改变量后重新部署。
- `vercel.json` 定义构建命令 `python3 build_static.py`、静态输出目录 `public` 和 Python API 配置。
- `build_static.py` 只复制网页资源，服务端密钥不会放入静态输出目录。
- 修改食物标签、模型问题和权重：编辑 `scoring.py`，同步更新推荐规则文档。
- 更新餐厅资料：编辑 `beichen_restaurants_2km_full.json`。价格、评分和营业信息来自静态资料，不会实时刷新。
