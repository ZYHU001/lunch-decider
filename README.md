# What for lunch？

手机优先的午饭餐厅选择网页，按 375×812 原型实现。顶部最多五张推荐卡片可左右滑动；剩余餐厅保留在底部的 1/3 大小卡片堆。网页现在从项目中的 beichen_restaurants_2km_full.json 加载 389 家北辰餐厅；以前浏览器里的示例清单不会再用于推荐，也不会被删除。底部最多展示 50 张未进入当前推荐的卡片。

## 启动

双击 `Start.command`，保持终端运行，然后打开 http://127.0.0.1:4173/。

也可以在项目目录运行：

```sh
LUNCH_DECIDER_HOST=0.0.0.0 python3 server.py
```

同 Wi-Fi 的手机通过 `http://电脑局域网IP:4173/` 访问。若已有旧服务占用 4173 端口，先关闭旧服务。

需要 Python 3.9 或更新版本，无第三方 Python 依赖。模型通过网络调用。

## Jev 与评分规则

`scoring.py` 保存用户给定的 `BASE_WEIGHTS` 和 `calculate_score` 规则。当前偏好标签、人数和辣度由网页传到服务端：

- 米饭/面食/热乎的/干净的/放纵的/重口的/吃肉/地方菜：对应 rice/noodles/warm/clean/indulgent/heavy_flavor/meat/regional。当前页面单选标签，服务端也支持这些布尔字段。
- 1 人启用 solo_friendly。
- 随机辣度不参与加权；😐 对应 0，一至五个辣椒对应 1–5。

Jev 用 Noul 返回标签与单人友好程度的 0–1 判断，用 Score 返回 0–5 的辣度。服务端用指定公式计算辣度匹配度；评分按 `(rating - 3.5) / 1.2` 限制在 0–1 内；距离 `distance_m` 使用米和给定分段规则。缺失评分或距离默认 0.5。激活的权重归一化后计算总分，返回排序最高的五家。总分是匹配分数，不是概率。

人数适配和预算仍是硬条件，辣度是软匹配条件。如果随机标签、随机辣度且不是单人用餐，只有评分与距离参与计算，这种情况不调用 Jev。距离使用数据集的 distance_m，不是用户实时位置。卡片图片从 photo_url 加载，失效或缺失时回退到午餐示意图。未知人数容量与辣度保留为空，由 Jev 根据品类、菜品标签和备注判断；缺少价格的餐厅显示“暂无价格”，暂不进入预算筛选。

## 配置

桌面版本在项目的 `.env` 保存 `TYPESAFE_API_KEY`，仅服务端读取。也可设置环境变量 `TYPESAFE_API_KEY` 或 `LUNCH_DECIDER_KEY_FILE`。服务只提供明确列出的网页资源，不会提供 `.env`。


## 卡片物理交互

进入页面时，50 张小卡片分批从顶部落下，落地后通过 Matter.js 0.20.0 碰撞与堆积。支持鼠标和手机触摸拖拽，释放时保留甩动速度，可撞开其他卡片。物理层位于筛选块后面，因此经过筛选块时会被遮挡。切换推荐结果保留其余卡片的物理状态，补充新卡片到 50 张；刷新页面或从浏览器缓存重新进入会重新掉落。引擎文件随项目保存，无需另行安装。
